## 1. High-Priority Audit: The SWS-Only HRV & Terminal-Cycle Claims

### 1.1 The SWS Selection Claim
- **Phase 14 Claim**: WHOOP calculates nightly HRV exclusively during Slow Wave Sleep (SWS / Deep Sleep).
- **Phase 15 Forensic Verdict**: **STRONGLY SUPPORTED as a Remote Cloud Methodology; CONTRADICTED as an On-Device Algorithm**.
  - **Instruction-Level Proof**: A full disassembly sweep of all 208 MB of `Whoop.app` confirmed **exactly zero mathematical routines for RMSSD** (`fsqrt`, sum-of-squares loops).
  - The string token `rmssd` appears in exactly 6 locations across the binary (`0x1096232a4`, `0x109633237`, `0x1099356b4`, `0x10a2207f4`, `0x10a223f54`, `0x10a22fd74`), all of which are DTO fields, Objective-C selectors, or JSON dictionary keys.
  - While sleep stage breakdowns exist (`SleepHRBreakdown` at `0x10a2c2486` cataloging `lightSleep`, `swsSleep`, `remSleep`, `awake`), there is **zero executable machine code connecting `swsSleep` to `heartRateVariabilityRmssd` on iOS**.
  - **Hardware to Cloud Pipeline**: Nordic BLE receives optical peak deltas extracted by the on-strap "SigProc" coprocessor (`0x1096128a7`) $\to$ decodes `RawDataRev21` (`0x1008d0000`) $\to$ streams raw time-series batches to AWS (`/activities-service/v2/activities`) $\to$ cloud ML model stages sleep and isolates SWS $\to$ returns finished scalar via `GET /users/v1/cycles` (`0x109633237`). The iOS app merely decodes and renders the value.

### 1.2 The "Terminal SWS Cycle" Claim
- **Phase 14 Claim**: WHOOP specifically selects/weights the final SWS cycle of the night.
- **Phase 15 Forensic Verdict**: **UNSUPPORTED INFERENCE FROM MARKETING / PODCASTS (INFERRED)**.
  - Sourced from WHOOP public communications (WHOOP Podcast Ep. 43: *The Science of HRV*), which states: *"It is weighted toward your last cycle of slow-wave sleep each night."*
  - **Binary Truth**: Neither `lastCycle`, `terminalSWS`, nor any equivalent temporal weighting rule exists in the iOS binary. The client binary cannot verify or disprove this cloud rule. It must **never** be cited as a reverse-engineered binary algorithm.

## 2. Core Forensic Answers

### What Do We Actually Know About WHOOP's Algorithms?
1. **Client is an Ingestion & Presentation Node**: The iOS app performs zero local time-series math for nocturnal RMSSD, Resting Heart Rate, Recovery score percentages, or VO₂ Max.
2. **Canonical Color Partitioning Is Executable On-Device**:
   - Disassembly of `-[WHPTheme recoveryColorForRecoveryScore:]` at `0x100041d3c`:
     ```assembly
     0x100041d64: ldr  d1, [x8, #0x578]   ; Load 33.0
     0x100041d6c: fcmp d0, d1
     0x100041d70: b.ls 0x100041da8        ; score <= 33.0 -> Red
     0x100041d84: ldr  d1, [x8, #0x4f0]   ; Load 66.0
     0x100041d88: fcmp d0, d1
     0x100041d8c: b.hi 0x100041da0        ; score > 66.0 -> Green
     ; Fall-through is Yellow (33.0 < score <= 66.0)
     ```
   - **Rounding Behavior**: The app does **not** round before classification; it evaluates raw IEEE-754 `Double` registers directly against `33.0` and `66.0`.
   - **`RecoveryLevel` Enum (`0x10a0f2874`)**: Formally defines 5 cases: `highRecovery` (0), `mediumRecovery` (1), `lowRecovery` (2), `calibrating` (3), `deadEnd` (4).
3. **Telemetry Hardware Validation**:
   - `RawDataRev21` parser at `0x1008d0000` enforces a hard limit of $\le 7$ RR intervals per second (`RRIntervalsCountTooLarge` at `0x1008d0a70`) and verifies that unused bytes in the 14-byte RR block are strictly zero (`RRIntervalsPaddingBytesNotAllZeroes` at `0x1008d0b8c`).
4. **Active Calorie & Strain Engine**:
   - `-[WHPActiveCalorieCalculator getCaloriesWithHeartRates:...]` (`0x109931877`) runs locally using revised Harris-Benedict BMR and Keyence equations, taking server-provided `restingHeartRate` as an input parameter.
   - `-[WHPTheme intensityColorForIntensityScore:]` (`0x100041ef0`) executes Day Strain tier partitioning at `9.9`, `14.9`, and `17.9`.

### What Did We Previously Assume (and Disproved in Phase 15)?
1. **Disproved**: That the iOS binary contains code selecting SWS for HRV. (Cloud-side only).
2. **Disproved**: That the "last SWS cycle" rule is verified code. (External marketing inference).
3. **Disproved**: That WHOOP rounds recovery scores before color classification. (Unrounded double comparison).
4. **Disproved**: That the ~16-minute sleep onset difference should be patched with a fixed offset. (It is physiological sleep latency from quiet rest to autonomic sleep, and must be resolved by autonomic heart rate gating, not hardcoded time offsets).

### Which Verified Changes Will Improve STRAP's Real-World Accuracy?
1. **Isolate Primary Sleep for Nightly HRV (Completed in `ebc9290`)**:
   Eliminating nap RMSSD weighting in `CaptureAnalysis.swift` prevents daytime naps from corrupting the overnight recovery reference.
2. **SWS-Constrained HRV Windowing**:
   Evaluating RMSSD over verified `.deep` (SWS) epochs closes the $-21\%$ gap between STRAP and WHOOP, aligning STRAP with WHOOP's parasympathetic measurement standard.
3. **28-Day Baseline Migration**:
   Moving STRAP's mature baseline window from 7 days to 28 days prevents acute variance explosion ($+130\%\ \sigma$) after single-night disruptions (alcohol, travel, illness), eliminating false Green recovery rebounds on subsequent days.
4. **Autonomic Sleep Onset Gate**:
   Requiring both stillness ($\text{accel} \le 0.10\text{ g}$) and cardiovascular deceleration ($\text{HR} \le \text{awakeRestingHR} + 5\text{ bpm}$) for 10 consecutive minutes resolves the ~16-minute onset discrepancy against WHOOP without fragile fixed offsets.
